# プロジェクト管理体制

このハッカソンの進め方の正本。迷ったらここに戻る。

---

## 0. この体制の設計思想

大会ルールから逆算した、3つの前提。

**前提1：審査軸が3つある＝管理項目も3つに割る。**
「問いの面白さ」「連鎖・創発の観測」「プロダクト化への近さ」は、それぞれ別の作業で伸びる。
コードを書き続けても①は伸びないし、③は最後に急に生まれたりしない。**3軸を別レーンで並走させる。**

**前提2：提出物が3点ある＝最後にまとめて作ると必ず落ちる。**
コード・可視化動画・解説文章。動画と文章を締切前に作り始めると、
「撮り直したいが実験を回す時間がない」で詰む。**設計時から3点を同時に育てる。**
特に解説文章は、設計ドキュメント（`docs/01_世界設計.md`）がそのまま母体になるように書く。

**前提3：シミュレーションは再現できて初めて「観測した」と言える。**
「創発が起きた」と主張するなら、審査員が同じ条件で再現できる必要がある。
**seedと設定をコミットしていない実験は、実験ではなく事故。**

## 1. 管理の中心単位は「タスク」ではなく「実験」

一般的なタスク管理をこのプロジェクトに持ち込まない。
このプロジェクトが積み上げるべき資産は、**実験の記録**である。

- 1実験 = 1 Issue = 1ディレクトリ（`experiments/EXP-00X/`） = 1つの実験カード
- 実験カードのテンプレは [`実験カード_テンプレート.md`](実験カード_テンプレート.md)
- カードには必ず書く：**仮説／変えた条件／seed／結果／創発の有無／次にやること**

この記録が、そのまま
- 解説文章の本文になり、
- 可視化動画のカット割りになり、
- 「連鎖・創発が観測できたこと」の証拠になる。

**実験を回したのにカードを書かない、が最大のリスク。** 回した直後に3行でいいから書く。

## 2. リポジトリ構成

```
hackathon/
├── README.md                      # 審査員が最初に読む入口。最後まで育て続ける
├── docs/
│   ├── プロジェクト管理体制.md      # このファイル
│   ├── 00_問い.md                  # 中心となる問い ← 審査軸①の正本
│   ├── 01_世界設計.md              # エージェント定義・世界のルール・環境 ← 解説文章の母体
│   ├── 02_観測設計.md              # 何を「創発」とみなし、どう測るか ← 審査軸②の正本
│   ├── 03_プロダクト構想.md         # 誰の何に使えるか ← 審査軸③の正本
│   ├── 実験カード_テンプレート.md
│   └── ADR/                       # 設計判断の記録（なぜそう決めたか）
├── experiments/
│   └── EXP-001_○○/
│       ├── config.yaml            # 実験条件（seed含む）※必ずコミット
│       ├── logs/                  # 実行ログ ※重いものは .gitignore
│       └── 所見.md                 # 実験カード
├── src/                           # シミュレータ本体
├── deliverables/
│   ├── 動画/                       # カット構成・素材・書き出し
│   └── 解説文章.md                  # 提出用レポート
└── .gitignore
```

**ドキュメントとコードを同じリポジトリに置く。** 別ツールに散らすと、締切前に必ず同期が切れる。

## 3. GitHub Projects：3レーン並走

ボードは1枚。列は進捗、**ラベルで3軸に割る。**

| ラベル | 意味 | 対応する審査軸 |
|---|---|---|
| `世界` | シミュレータの実装・世界ルールの設計 | ①問いの面白さ |
| `観測` | 実験の実行・指標の設計・可視化 | ②連鎖・創発 |
| `提出物` | 動画・解説文章・README | ③プロダクト化 ＋ 伝達 |

列：`Backlog` → `今週` → `進行中` → `検証待ち` → `完了`

**ルール：`進行中` は同時に2枚まで。** 個人でも小チームでも、3枚並ぶと全部止まる。

**毎週、3軸それぞれの `完了` 枚数を見る。** どれかが0のまま2週続いたら、その週はその軸に全振りする。

### 4.1 6日計画で捨てたもの・死守するもの

**捨てた：発散フェーズ（3案を回して選ぶ）。** → `ADR/ADR-002` に理由を記録。
6日で3案を回すと、どれも証拠が薄いまま締切を迎える。**1案に賭けて、証拠を厚くする。**

**死守：この3つ。順番も変えない。**

1. **初日に連鎖ログを作りきる。** 「誰の発言が誰を動かしたか」の参照関係をイベントに埋める。
   **これは後から足せない。** 実験を5回回した後に気づいたら、その5回は全部やり直しになる
2. **初日〜2日目に可視化を作る。** 可視化があれば以降の実験が全部が動画素材になる。
   最後に作ると、撮り直しのきかない1テイクしか手に入らない
3. **8/27(木) の機能凍結。** ハッカソンで落ちる典型は「前日に新機能を入れて壊れ、動画も文章も間に合わない」。
   凍結後は `hotfix/` で最小修正のみ

### 4.1.1 1日でも遅れたときの切り捨て順

遅延は起きる前提で、**捨てる順番を先に決めておく**。上から捨てる。

1. 指標4つのうち「相互作用の偏り」「役割分化」 → **語彙の定着 と 連鎖の深さ だけ残す**
2. アブレーション以外の追加条件振り
3. シード3本 → 2本（1本にはしない。1本は事故と区別できない）
4. **脱文脈テストは最後まで捨てない。** ここが差別化点なので、これを捨てるなら他の全部を捨てる

### 4.2 提出物3点は初日から並走させる

| 提出物 | いつ育てるか |
|---|---|
| ①ソースコード | 8/24 に骨格。**8/27 の凍結以降は触らない** |
| ②可視化動画 | 8/24-25 に自動生成の仕組み → 毎実験がテイクになる → 8/29 に3シーン選ぶだけ |
| ③解説文章 | `docs/01_世界設計.md` と実験カードが母体。**8/29 に書き始めない。清書するだけ** |

**6日計画では、この並走が「守れたら良いこと」ではなく前提になる。**
最終日に3点を作ろうとすると、確実に1点落ちる。

### 4.3 AI評価エージェントを読者として想定する

本大会は人間の審査に加え、**Claudeベースの AI 評価エージェント**が入る。
AIは世界観の壮大さより **主張と証拠の対応** を正確に読む。したがって README は次の形に固定する。

> **主張 → 根拠ファイルへのリンク → 再現する1コマンド**

「創発が観測された」と書いたら、その隣に実験カードへのリンクと、それを再現するコマンドを必ず置く。
リンクと再現手段のない主張は、AI読者には**書いていないのと同じ**。

## 5. リズム

**毎日（15分）**
1. 昨日の実験結果を実験カードに追記する
2. 今日回す実験を1つ決めて Issue を `進行中` に動かす
3. 気づきを1行 `docs/00_問い.md` に足す（問いは育つもの）

**毎晩（10分）— 6日計画では週1レビューを毎晩に置き換える**
3軸を5点満点で自己採点し、記録する。翌日の配分を決める。

| 軸 | 問い |
|---|---|
| ①問いの面白さ | この問いを人に話したとき、相手は続きを聞きたがるか |
| ②連鎖・創発 | 「設計していないのに起きたこと」を1つ挙げられるか |
| ③プロダクト化 | 誰が、どんな場面で、これに金を払うか言えるか |

**一番低い軸に、翌週の時間を優先配分する。** 得意な軸だけ伸ばしても総合点は上がらない。

## 6. Git 運用

- `main` は常に動く状態を保つ。デモ・提出はここから
- `feat/<内容>` で切って `main` へPR（個人参加ならセルフマージで可。**PRは作る**：差分の記録が解説文章の材料になる）
- `exp/EXP-00X` は実験専用。捨ててよい
- コミットメッセージは日本語で可。「何を変えたか」より **「なぜ変えたか」** を書く
- **`config.yaml` と seed は必ずコミット。** ログの生ファイルが重い場合は要約だけコミットする

## 7. リスクと対策

| リスク | 兆候 | 対策 |
|---|---|---|
| **LLM APIコストの暴走** | マルチエージェント×多ターンでトークンが指数的に増える | 実験1回あたりのトークン上限を先に決める。まず小規模（エージェント数・ターン数を最小）で回し、挙動を確認してから本番規模へ |
| **再現できない** | 「あの時いい結果が出たのに再現しない」 | seed固定。config を実行前にコミット。ログにモデル名とバージョンも残す |
| **問いが決まらないまま時間が溶ける** | D-8を過ぎても案が2つ以上ある | 問い確定ゲートを死守。決めきれなければ「実験カードの枚数が多い方」を機械的に採用 |
| **提出物が間に合わない** | D-4時点で動画のカット構成が白紙 | 機能凍結を死守。動画は「実験カードの中から3シーン選ぶ」だけで組めるよう、日々カードを書いておく |
| **属人化・単一障害点** | 1人しか触れないコードがある | 【要確認】チーム構成が決まったら、最低限 `src/` の起動手順を README に書き、他メンバーが動かせる状態にする |
| **知財・公開範囲の事故** | 公開してよいか不明なまま GitHub を public にする | **【要確認】** 大会規定を確認するまで **private のまま**にする |
